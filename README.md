# God Damn Repackager

> **⚠️ ALPHA 版本**
> 本模组目前处于早期测试阶段。它通过 Mixin 修改机械动力（Create）的理包机核心逻辑，
> **尚未经过大规模、长时间的稳定性测试**。已知风险包括（但不限于）：
> - 在未预见的边界场景下可能导致**物品丢失或异常**
> - 与特定版本的机械动力或其它模组可能存在兼容性问题
> - 游戏崩溃、世界存档异常
>
> **使用前请务必备份你的存档。** 作者不对因使用本模组造成的任何数据损失负责。
> 如果遇到 bug，欢迎在 GitHub Issues 提交（附上 `crash-reports/` 下的崩溃报告和游戏日志）。
>
> **ℹ️ 如果你用过 0.2.0：** 0.2.0 在已存在的存档（尤其多人服务器）里可能出现"下单后只有部分
> 理包机工作"的问题，当时需要手动重新放置理包机。**0.2.1 已修复此问题**，升级后无需任何操作。
> 详见下方[已知限制](#已知限制)。

一个让 Create 6.0+ 的理包机（Repackager）并行处理同一保险库（Vault）大批量合成订单的模组。
N 个理包机 ≈ N 倍合成速度。**同时提供 Forge 1.20.1 和 NeoForge 1.21.1 两个版本。**

---

## 支持的平台与版本

本模组为两个 MC / 加载器组合各维护一个版本，功能完全一致。请根据你的游戏环境选择对应的 jar。

| | Forge 版本 | NeoForge 版本 |
|---|---|---|
| **Minecraft** | 1.20.1 | 1.21.1 |
| **加载器** | Forge 47.x | NeoForge 21.1.x |
| **Create（必需依赖）** | 6.0.x（已测试 6.0.8） | 6.0.x（已测试 6.0.10） |
| **模组版本号** | `0.5.0-forge` | `0.5.0-neoforge` |
| **jar 文件名** | `goddamnrepackager-0.5.0-forge-alpha.jar` | `goddamnrepackager-0.5.0-neoforge-alpha.jar` |
| **维护分支** | `master` | `neoforge-1.21.1` |

> 两个版本选哪个取决于你玩的整合包用 Forge 还是 NeoForge。
> 如果你不知道选哪个：单人/新整合包推荐 NeoForge 1.21.1（更新、更现代）；
> 老存档或已有 Forge 整合包继续用 Forge 1.20.1。
>
> 两个版本功能完全一致：共享包裹池并行（0.4.0）+ 部分重组（0.5.0，材料到一部分就提前开工，见下文）。

## 这个模组解决什么问题

在原版机械动力 6.0+ 中，当你通过仓库管理员（Stockkeeper）对一个合成器阵列下达一个大批量合成订单时
（例如"合成 1000 个铁块"），**整张订单只会被一个理包机（Repackager）处理**。即使你的输入保险库
周围贴满了理包机，也只有其中一个在忙活，其余的全部闲置。一个理包机每秒只能输出一个包裹（动画周期
20 ticks），所以大订单要等很久。

本模组让**同一保险库上的所有理包机并行分担**这张订单。N 个理包机 ≈ N 倍的处理速度。

### 效果对比

| 场景 | 原版 | 加上本模组 |
|---|---|---|
| 1000 个合成，1 个理包机 | ~1000 秒 | ~1000 秒（无变化） |
| 1000 个合成，3 个理包机 | ~1000 秒（其余 2 个闲置） | ~333 秒 |
| 1000 个合成，9 个理包机 | ~1000 秒（其余 8 个闲置） | ~111 秒 |

## 工作原理（简述）

理包机在整理订单时会一次性把整张订单的合成包裹塞进**自己的**发送队列，然后每秒发出一个。
本模组改为把整批包裹放进一个**按保险库区分的共享池**（0.4.0 架构）：

- **入池**：理包机整理好订单后，整批包裹不再进自己的私有队列，而是存入世界级的共享包裹池
  （按保险库身份区分）。
- **按需取**：每个空闲理包机每 tick（50ms）从共享池里取一个包裹放进自己的私有队列，然后照常
  发送。N 个理包机就能同时发包，N 台 ≈ N 倍速度。
- **动态均衡**：共享池天然就是动态均衡——空闲理包机主动取活，堵塞的理包机（下游通道断）被
  `heldBox` 非空挡住不取新包，活自动流向空闲兄弟。

**部分重组（0.5.0 新增）：** 原版理包机要等一张订单的**全部**原料碎片到齐
才开始整理（all-or-nothing）。大订单的碎片经运输网络分批到达，"等最后一片"往往要很久。0.5.0
让理包机在**已到碎片够合成至少一次**时就提前开工：已到的材料先合成先发，后续碎片到达一批就
接着合成一批，直到整单完成。大订单的等待时间因此大幅缩短——并行（多台分担）之外又多了
"提前开工"这一层提速。订单材料全程守恒：未用完的原料托管在世界存档里，拆掉保险库会如数爆出。

> **关于"打掉理包机"的行为（0.4.0 新增，重要）：** 共享池是**跟随存档**而非跟随方块的，所以
> **打掉理包机不会爆出共享池里的包裹**——池里的包安全留存，重新放回理包机即可继续处理。只有
> 当**保险库本身被破坏（打掉方块或扳手拆除）**时，该保险库对应的共享池里的包裹才会作为实体掉落。
> 扩建保险库（加减方块改变形状）不会掉落包裹——池会自动迁移到新形状，理包机继续处理。理包机
> 遵循机械动力原版设计：需要红石信号才会工作。

详细的技术实现见 [TECHNICAL.md](TECHNICAL.md)。

## 安装

两个版本的安装步骤相同，只是 jar 和依赖版本不同：

1. 安装对应版本的 **Minecraft + 加载器**（见上方[支持的平台与版本](#支持的平台与版本)表）
2. 安装 **Create 6.0.x**（必需依赖，版本见上表）
3. 把对应版本的 `goddamnrepackager-*.jar` 放进 `.minecraft/mods/` 文件夹
4. 启动游戏

> **从 0.2.0 升级？** 直接替换 jar 即可。0.2.0 曾要求在老存档里重新放置理包机，
> 0.2.1 已修复此问题，升级后无需任何额外操作。详见下方[已知限制](#已知限制)。

不需要任何配置，开箱即用。

## 使用方法

**不需要任何额外操作。** 像平时一样搭你的合成器阵列：

```
[总仓库] ──订单──> 蛙港发货 ──> 输入保险库(装着原料包裹)
                                       ↓
                            多个理包机(贴红石块常开)
                                       ↓
                            打包机(拆包) ──> 动力合成器 ──> 产物
```

只要输入保险库周围有多个理包机，本模组就会自动让它们并行工作。

## 已知限制

- ~~**安装到已存在的存档后，需要重新放置理包机。**~~ **（0.2.1 已修复）** 0.2.0 在老存档
  （尤其多人服务器）里可能出现"下单后只有部分理包机工作"（例如 9 个只有 6 个工作），当时需要
  手动重新放置理包机。根因是 sibling 判定用了脆弱的 `IItemHandler ==`（能力实例代次敏感）。
  **0.2.1 改用 Create 的 `InventoryIdentifier` 值相等判定同库，此问题不再出现，升级即可，无需
  重新放置。** 技术细节见 [TECHNICAL.md §3.7](TECHNICAL.md)。
- ~~当前实现是"一次性快照分配"，分配完就静态，空闲理包机不会去抢别人的活。~~
  **（0.3.0 已改善，0.4.0 彻底重构）** 0.3.0 在快照分配之上叠加了**动态再平衡**；0.4.0 进一步改为
  **共享包裹池**架构（整批入池 + 各机按需取），天然实现动态均衡，不再需要快照分配和再平衡两套逻辑。
- **打掉理包机不会爆出共享池里的包裹（0.4.0 新增，请留意）。** 共享包裹池存在世界存档里，
  与方块独立。打掉理包机时只会爆出它手上正在发送的那 1 个包裹（heldBox），共享池里还没处理的
  包裹**不会爆出**，而是安全留在池里——重新放回理包机即可继续处理，不会丢失。只有当**保险库
  本身被破坏（打掉方块或扳手拆除）**时，该保险库对应的共享池里的包裹才会作为实体掉落。
- **扩建保险库（reshape）现在会自动跟随（0.4.0 已修复）。** 给保险库加减方块改变形状时，旧形状
  对应的共享池会自动迁移到新形状的 key 上，池里的包裹继续被理包机处理，不会丢失也不会爆出来。
  技术细节见 [TECHNICAL.md §3.9⑥](TECHNICAL.md)。
- **部分重组进行中的订单需要至少一台充能理包机（0.5.0）。** 一张订单一旦被"接管"（开始渐进
  合成），就需要保险库周围至少一台红石充能的理包机持续工作才能推进到完成。如果中途把所有
  理包机拆掉或断掉红石，订单会暂停——未用完的原料安全托管在世界存档里（拆保险库会爆出），
  重新放回理包机并充能即可继续。纯物品订单（不含合成配方）不会被接管，行为与原版一致。
- 理包机必须贴在**机械动力的保险库（Vault）**上。其它容器（板条箱、原版箱子）理论上也支持，
  但尚未充分测试。

## 调试

如果需要排查问题，可以在 `GodDamnRepackager.java` 里把 `DEBUG_LOGGING = true` 重新编译。
开启后每次入池/取包都会在日志里打印 `[GDR-POOL]` 行：`deposited`（理包机整理后入池）、
`fed`（空闲理包机取包）、`drained & dropped`（保险库销毁/扩建时爆出池里包裹）。
0.5.0 部分重组另有 `[GDR-PARTIAL]` 行：`crafted`（渐进合成了一批）、`final pass`（订单收尾
完成）、`drained`（保险库销毁时爆出托管原料）、`migrated`（保险库扩建时迁移订单状态）。
